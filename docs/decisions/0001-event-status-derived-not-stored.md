# ADR 0001：活动状态读取时推导，不落库

- 状态：已采纳
- 日期：2026-10-19

## 背景

一场活动同时有四个时间边界：报名截止、开始、结束，以及队长可能随时执行的取消。
列表和详情都要回答「现在能不能报名」「是不是已经开始了」。

把 `status`（OPEN / ONGOING / FINISHED / CLOSED / CANCELLED）存成一列，需要有人
在边界时刻把它改掉：定时任务、写接口顺带更新、或数据库事件。任何一次漏跑、
时钟偏差或并发写都会让列和真实时间不一致，而这类不一致恰好发生在用户最敏感的
时刻（截止前一秒、开赛瞬间）。

## 决策

状态不落库。每次读取时，由 `deriveEventStatus` 根据 `now` 与四个时间点计算：

```text
CANCELLED   cancelledAt 非空
FINISHED    now >= endAt
ONGOING     now >= startAt
CLOSED      now >= signupDeadline
OPEN        其余情况
```

- `now` 作为参数注入，函数本身不读系统时钟，测试可以用固定时间覆盖每个边界 ±1ms。
- 取消是队长做过的动作，优先于一切时间判断。
- 列表、详情、按钮判定共用同一个函数，服务端只有这一份推导。
- 数据库只存事实：`start_at`、`end_at`、`signup_deadline`、`cancelled_at`。

## 后果

- 没有任何状态推进任务；活动从 OPEN 走到 CLOSED 不需要写库。
- 每次读都是准确的，不会出现「已经过了截止时间但状态还是 OPEN」。
- 不能直接用 SQL 按状态筛选；按时间范围建索引，状态在应用层推导。本案例数据量
  很小，列表直接读取后在内存中排序。真实产品若需要按状态分页，可把时间条件翻译成
  SQL 的 `WHERE`，仍然不需要状态列。
- 多实例部署时 `now` 来自各自进程的时钟。生产环境应统一取数据库时间或 NTP 校准；
  本案例是单进程演示。
- 已结束的活动仍能看到自己的报名记录，只是按钮置灰——状态推导与报名记录是两件事。

## 备选方案

- **定时任务改状态**：边界时刻会抖动，任务失败就漂移；还要处理补跑与并发。
- **数据库生成列**：仍然依赖数据库时钟，且取消会覆盖时间推导，需要额外优先级逻辑。
- **客户端推导**：用户改系统时间就能看到错误状态；9 种状态的规则也会出现第二份实现。
