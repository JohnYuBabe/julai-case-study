# ADR 0003：9 种按钮状态由服务端一次判定

- 状态：已采纳
- 日期：2026-10-19

## 背景

报名按钮看似只有一个，实际有 9 种状态：活动取消、已结束、我是队长、已报名、候补中、
报名关闭、可加入候补、访客可报名、登录后可报名。它同时取决于：

- 活动的时间阶段（见 ADR 0001）
- 名额与候补队列
- 当前用户是谁（访客 / 普通用户 / 队长）
- 当前用户的报名记录

如果客户端自己组合这些条件，规则会出现第二份实现：列表、详情、App、小程序各写一遍，
任何一处漏掉「已结束优先于已报名」就会显示一个点不动的按钮，或者给出与服务端冲突的
文案。

## 决策

按钮状态是一个**共享契约**，判定发生在服务端：

```text
packages/shared
  BUTTON_STATES / ButtonState / ButtonView
  resolveButtonState(input) → ButtonView
        ▲                    ▲
        │                    │
   server 调用           web 只读类型
        │
  GET /api/events/:id → { event, viewer, registration, button }
```

- `resolveButtonState` 是纯函数，`now` 由调用方注入，优先级固定为：
  已取消 > 已结束 > 队长 > 已报名 > 候补中 > 已开始 > 已截止 > 满员 > 可报名。
- 服务端把 `state`、`label`、`variant`、`action`、`requireAuth`、`confirm`、
  `confirmText` 一次算完，作为 `button` 字段下发。
- 前端不判断状态，只渲染 `button`。点击时按 `button.action` 调对应接口。
- 队长只看到「管理本期活动」。三个写接口统一返回
  `ORGANIZER_CANNOT_PARTICIPATE`，避免按钮说管理、接口却允许报名。
- 候补位次：数据库的 `waitlist_seq` 是只增不减的票号，用于 FIFO 转正；下发给用户的
  `button` 文案与 `registration.waitlistRank` 都是当前活跃队列中的实际排位。退出后重新加入会拿新票号，排到队尾。

## 后果

- 客户端非常薄：换框架、做小程序、写测试都只消费同一份 `ButtonView`。
- 接口响应自带展示信息，详情页首屏不需要二次请求或本地推导。
- 新增一种状态时，`Record<ButtonState, ButtonStateMeta>` 会让 `tsc` 在漏写元数据时
  失败；契约测试覆盖 9 态可达、优先级和三处时间边界。
- 文案与样式由服务端主导，客户端想改文案需要改共享包。这是有意的：避免两端漂移。
- `waitlistCount` 在列表里表示「已发出的候补号数量」，不是当前排队人数；展示时
  必须按这个语义写，否则退出候补后数字会对不上。
- 演示前端额外提供了「9 态矩阵」页：对 9 组固定夹具分别请求真实详情接口，把契约
  状态与实际 `button` 并排显示。数据被改动时会显式标红，而不是静默错位。

## 备选方案

- **客户端各写一份判定**：规则重复，时间边界与登录态最容易漂移。
- **后端只返回布尔字段**（canSignup、isFull…）：客户端仍要组合优先级，9 态会退化成
  一堆 if。
- **GraphQL 让客户端选字段**：不解决「谁来判定」的问题，只是换了传输层。
